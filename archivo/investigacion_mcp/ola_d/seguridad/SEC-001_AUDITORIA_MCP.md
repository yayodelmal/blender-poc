# SEC-001 — Auditoría estática de MCP for Blender
**Fecha de consulta:** 2026-11-02. **Alcance:** fuentes públicas; no se instaló, ejecutó, conectó ni configuró nada. **Versión auditada:** no se pudo fijar release/commit; conclusiones de código `main` son solo observación de rama mutable.

## Dictamen

**INCONCLUSO para candidato 2.2.6.** No hay releases publicados en GitHub, la consulta de tags/API no fue accesible y no se recuperó SHA completo. El manifiesto de `main` dice 2.2.6, pero eso no identifica un artefacto reproducible ni confirma que el addon correspondiente sea el mismo código. El issue #404 es específico de 1.6.0 y demuestra el patrón reportado ahí; no establece aplicabilidad a 2.2.6. Tampoco se pudo auditar el addon empaquetado actual completo mediante el lector web.

La observación defensiva sobre `main` muestra un cliente socket MCP con host por defecto `localhost`, opciones `--host` y `BLENDER_HOST`, y puerto 9876. El código del servidor documenta y registra que `execute_blender_code` pasa código al addon. La seguridad del listener en addon no queda verificada de forma suficiente en esta revisión. En consecuencia, no se autoriza EXP-001 basándose en este informe.

El nombre canónico es [ahujasid/mcp-for-blender](https://github.com/ahujasid/mcp-for-blender); el nombre antiguo `ahujasid/blender-mcp` redirige. La página de [releases](https://github.com/ahujasid/mcp-for-blender/releases) consultada informa “There aren’t any releases here”. Tags y endpoints API no pudieron recuperarse desde la fuente usada en esta investigación. El [pyproject en main](https://github.com/ahujasid/mcp-for-blender/blob/main/pyproject.toml) declara paquete 2.2.6 y lista `src/blender_mcp/bundled/addon.py` como paquete de datos; no se verifica por ello un wheel, tag, SHA ni correspondencia servidor/addon. El archivo `server.py` en GitHub marca `main`, sin SHA visible en contenido recuperado. No se puede llamar a esto auditoría de versión 2.2.6.

## Límites de confianza y respuesta a SEC-03/04

Codex decide invocaciones y usa servidor MCP; servidor Python valida/construye llamadas y mantiene conexión TCP al proceso Blender; addon recibe la solicitud y ejecuta dentro de Blender. A falta de token/ACL corroborados en código candidato, cualquier proceso capaz de alcanzar listener es potencial cliente. “Localhost” reduce superficie de red según resolución/bind, pero no autentica otros procesos de la misma máquina, ni protege de otro usuario con acceso local.

En `main`, Python arbitrario en Blender equivale a capacidades del proceso: API Blender, archivos alcanzables y subprocess/red si el runtime/OS no lo impide. No encontré evidencia verificable de sandbox OS, allowlist obligatoria o autorización independiente por operación. `safe_mode_enabled()` parece una regla de instrucción/filtrado desde server, pero no se auditó suficientemente para declarar restricción efectiva del cliente conectado. Separación read-only/write no es límite de seguridad acreditado.

## SEC-05/06, telemetría y dependencias

- #404 sigue abierto en la consulta y el panel “Development” no lista rama/PR; esto no prueba que no exista una corrección fuera de vínculos visibles, pero no hay referencia rastreable a fix. [Issue](https://github.com/ahujasid/mcp-for-blender/issues/404).
- `pyproject` declara Python ≥3.10, dependencias `mcp>=1.26,<2`, `httpx>=0.27`; `main` addon integra requests/servicios de assets. Una llamada básica de inspección no necesita generación externa conceptualmente, pero comprobar importaciones, conexiones de arranque y defaults requiere auditar release completa.
- README actual describe contenido (prompts, código, capturas, trajectory) como opt-in; metadatos mínimos anónimos como default; variable `DISABLE_TELEMETRY=true` para apagarlo todo. No inspeccioné tráfico ni confirmo este comportamiento en paquete 2.2.6.
- Addon contiene integración con Poly Haven/Meshy/Tripo/Poly Pizza en fuente actual; son acciones externas que no son necesarias para modelado geométrico local. La seguridad de API keys/descargas queda fuera del análisis exhaustivo y deben quedar deshabilitadas/no invocarse en laboratorio.

## Mitigaciones respaldadas / estado

`localhost` es default del cliente en `main`; la dirección listener del addon no se confirmó. CLI/env `--host`/`BLENDER_HOST` son soportados por cliente y deben limitarse al loopback que acepte implementación examinada. No documenté “loopback garantizado”. Telemetry-off es configuración documentada en README mutable. No encontré una forma acreditada de deshabilitar el sink Python por completo ni una allowlist efectiva. Sesión macOS separada, permisos mínimos, no túneles/LAN, cerrar addon y servidor reducen exposición operacional pero no corrigen falta de autenticación ante procesos locales.

## Limitaciones metodológicas

Revisión estática de documentos/HTML GitHub y extractos de fuentes; no descarga raw, checkout ni análisis de AST completo porque fuente exacta no pudo fijarse. No ejecución de código, red/socket, instalación ni pruebas. No se calcularon CVSS; severidad cualitativa considera ejecución arbitraria con privilegios de proceso y frontera de red local. La página issue contiene una demostración histórica, pero esta auditoría no la reprodujo.

## Resultado

El comportamiento de 1.6.0 reportado en #404 sería incompatible con EXP-001 sin control adicional. El estado de la versión candidata 2.2.6 es **INCONCLUSO** por falta de release/SHA y código addon verificable.
